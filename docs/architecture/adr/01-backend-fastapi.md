# ADR-01: Выбор FastAPI для backend

- **Статус:** Принято
- **Дата:** 2026-10-17

## Контекст

Нужен небольшой self-hosted backend для изолированной сети. MVP должен предоставлять REST API, forward-auth endpoint, OpenAPI-документацию, RBAC, аудит, работу с SQLite и криптографические операции. Внешние облачные зависимости недопустимы, а развёртывание должно быть возможным в Docker или офлайн-установщике.

Рассматривались FastAPI, Django и Go. Сравнение приведено в [technologies.md](../../literature-review/technologies.md).

## Решение

Выбрать **FastAPI** как серверную платформу MVP. Использовать явные Pydantic-схемы для входных данных и автоматически генерируемую OpenAPI-схему. Криптографию, хранение секретов, rate limiting и авторизацию реализовать через отдельные модули с тестами; не считать наличие FastAPI заменой security controls.

## Последствия

Положительные:

- быстрый путь к типизированному REST API и проверке данных;
- небольшой объём приложения и удобный offline/container deployment;
- Python-экосистема для Argon2id, TOTP, AES-GCM, QR и SQLite;
- проще реализовать исследовательский MVP и его тесты.

Отрицательные и компенсирующие меры:

- безопасность MFA/RBAC не предоставляется автоматически: добавить отдельные сервисы, dependency checks, аудит и security-тесты;
- неправильное применение async может блокировать event loop: блокирующие операции выполнять в синхронном слое или thread pool;
- Python runtime и зависимости нужно фиксировать lock-файлом и поставлять в offline image/wheel cache.

## Альтернативы

- **Django:** зрелый монолит, ORM и admin, но для узкого MFA API добавляет больше компонентов и конфигурации.
- **Go:** удобен для единого бинарника и высокой конкуренции, но потребует больше собственного кода для ORM, admin workflow, схем и криптографических интеграций.
