# ADR-02: Выбор SQLite для MVP

- **Статус:** Принято для MVP
- **Дата:** 2026-10-17

## Контекст

Сервис предназначен для автономной установки внутри LAN. Ожидаемый MVP — один экземпляр приложения с пользователями, зашифрованными TOTP-секретами, резервными кодами, RBAC и audit log. Внешний database server не должен быть обязательным компонентом офлайн-установки.

Рассматривались SQLite и PostgreSQL. Критичны транзакционность проверки TOTP, атомарное предотвращение повторного использования кода, резервное копирование и возможность перейти к нескольким экземплярам позже.

## Решение

Использовать **SQLite** как базу данных MVP. Включить транзакции и подходящий режим журналирования, применять миграции и выполнять резервное копирование защищённого файла базы. Проверку TOTP и запись использованного временного шага выполнять атомарно. Ключ AES-256-GCM хранить вне базы и не записывать в audit log.

## Последствия

Положительные:

- минимальное число компонентов и простой однокомандный deployment;
- полностью локальная работа без PostgreSQL-сервера;
- удобное резервное копирование одного файла и переносимость в air-gapped среде;
- достаточная модель для single-node MVP.

Ограничения:

- ограниченная конкуренция записи и отсутствие штатного горизонтального масштабирования;
- нужен контроль доступа к файлу, backup policy и проверка восстановления;
- нельзя размещать базу на ненадёжном общем сетевом файле;
- для нескольких экземпляров потребуется PostgreSQL и отдельная стратегия миграции.

## Альтернатива

**PostgreSQL** лучше подходит для высокой конкуренции, нескольких экземпляров, централизованных backup и будущего SIEM/audit pipeline, но требует отдельного сервиса, volume, настройки и сопровождения. Поэтому он остаётся масштабируемой альтернативой, а не базовой зависимостью MVP.
